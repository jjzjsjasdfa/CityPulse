# CityPulse backend structure

This guide explains the backend as it exists today. It is written for someone
who is new to FastAPI, SQLModel, Alembic, and Docker.

## 1. The big picture

The backend receives HTTP requests from the mobile application, validates them,
reads or writes PostgreSQL, and returns JSON.

```text
React Native application
        |
        | HTTP request, such as GET /api/v1/events
        v
Uvicorn web server
        |
        v
FastAPI application: app/main.py
        |
        v
API router: app/api/router.py
        |
        v
Route function: app/api/routes/*.py
        |
        v
SQLModel session: app/core/database.py
        |
        v
PostgreSQL + PostGIS
```

The four layers to remember are:

1. **Routes** decide what an endpoint does.
2. **Schemas** define the JSON accepted and returned by the API.
3. **Models** define how records are stored in PostgreSQL.
4. **Migrations** change the real database structure over time.

## 3. Files at the backend root

### `backend/Dockerfile`

Defines how Docker builds the API image. It starts with Python 3.13, installs
the packages from `pyproject.toml`, copies the source and migrations, exposes
port 8000, and defines the container startup command.

At startup, the container runs these commands in order:

```text
alembic upgrade head
    -> python -m app.seed
        -> uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Because they are joined with `&&`, the API will not start if a migration or the
seed step fails.

### `backend/pyproject.toml`

Describes the Python project and its dependencies.

Runtime dependencies include:

- FastAPI for HTTP APIs
- SQLModel for database models and queries
- Psycopg for connecting to PostgreSQL
- GeoAlchemy2 for PostGIS types and functions
- Alembic for database migrations
- Pydantic Settings for environment configuration

The optional `dev` group adds pytest, Ruff, and HTTPX for tests and development.
The same file also configures pytest and Ruff.

### `backend/uv.lock`

Records the exact resolved version of every Python dependency. `pyproject.toml`
says which version ranges are allowed; `uv.lock` makes installations
reproducible by recording the versions that were actually selected.

Do not edit this file manually. `uv sync` updates it when dependencies change.

### `backend/README.md`

Contains short backend startup instructions and links to `/docs`, `/health`,
and `/openapi.json`.

### `backend/alembic.ini`

The top-level Alembic configuration. It tells Alembic where migration files are
located and how migration logging should be formatted. The database URL itself
is supplied by `app/core/config.py` in `alembic/env.py`.

## 4. Application entry point

### `backend/app/__init__.py`

Marks `app` as a Python package. It is intentionally empty.

### `backend/app/main.py`

This is the main entry point for the API. Uvicorn loads the `app` object from
this file using `app.main:app`.

It is responsible for:

- creating the FastAPI application
- setting the application name, description, and version
- configuring CORS for permitted frontend origins
- mounting all `/api/v1` routes
- converting HTTP and validation errors to a consistent JSON shape
- providing `GET /health`
- providing the small root response at `GET /`

The health endpoint executes `SELECT 1`. Therefore, `/health` only succeeds if
the API can actually connect to PostgreSQL.

The shared error format is:

```json
{
  "error": {
    "code": "http_404",
    "message": "Event not found",
    "details": null
  }
}
```

## 5. Core configuration and database access

### `backend/app/core/__init__.py`

Marks `core` as a Python package. It is intentionally empty.

### `backend/app/core/config.py`

Defines application settings using Pydantic Settings.

Important settings are:

- `app_name`: displayed in the OpenAPI documentation
- `api_v1_prefix`: currently `/api/v1`
- `database_url`: tells SQLAlchemy how to reach PostgreSQL
- `backend_cors_origins`: browser origins allowed to call the API

Environment variables override the defaults. Inside Docker, the database URL
contains `@db:5432` because `db` is the Compose service name. Outside Docker,
the default uses `localhost:5432`.

`get_settings()` is cached so the environment is parsed once per process.

### `backend/app/core/database.py`

Creates the shared SQLAlchemy database engine:

```python
engine = create_engine(settings.database_url, pool_pre_ping=True)
```

The engine owns the connection pool. `pool_pre_ping=True` checks a connection
before reusing it, avoiding many errors caused by stale connections.

`get_session()` creates one SQLModel session for a request and closes it when
the request finishes. Routes receive it through FastAPI dependency injection:

```python
SessionDep = Annotated[Session, Depends(get_session)]
```

## 6. Database models

### `backend/app/models.py`

Defines the Python classes mapped to PostgreSQL tables. A class with
`table=True` represents a real database table.

| Model | Database table | Purpose |
| --- | --- | --- |
| `Event` | `events` | Stores an activity, its time, venue, status, coordinates, and trust metadata |
| `Source` | `sources` | Stores an evidence publisher or source |
| `EventSourceLink` | `event_source_links` | Connects an event to one or more sources |
| `StatusHistory` | `status_history` | Preserves event status changes over time |
| `Correction` | `corrections` | Stores user-submitted corrections for review |

It also defines enums that restrict values:

- `EventCategory`: performance, sports, exhibition, festival, and others
- `EventStatus`: announced, on sale, sold out, postponed, cancelled, or ended
- `SourceLevel`: authority, trusted, or unverified lead
- `CorrectionStatus`: pending, reviewing, accepted, or rejected

The `Event.location` column is a PostGIS `geography(POINT, 4326)` value. `4326`
is the standard longitude/latitude coordinate reference system used by GPS.

`Event.traits` is stored in a PostgreSQL JSONB column named `attributes`.
Examples include `免费`, `户外`, and `亲子友好`.

### Models are not migrations

Changing `models.py` changes Python's understanding of the database, but it
does not automatically change an existing PostgreSQL database. A matching
Alembic migration must be created and applied.

## 7. API schemas

### `backend/app/schemas.py`

Defines Pydantic models for HTTP request and response bodies. These models do
not create tables.

Important schemas include:

- `EventSummary`: compact event representation used in the feed
- `EventDetail`: summary plus description, sources, and status history
- `EventPage`: event list plus pagination metadata
- `MapEvent`: smaller representation used for map markers
- `CorrectionCreate`: validates a submitted correction
- `CorrectionResponse`: confirms that the correction entered the queue
- `ApiErrorResponse`: documents the shared error shape

FastAPI converts these schemas into OpenAPI. That contract is then converted
into TypeScript types for the mobile application.

Keeping schemas separate from database models prevents private database fields
from accidentally appearing in public API responses.

## 8. API routing

### `backend/app/api/__init__.py`

Marks `api` as a Python package. It is intentionally empty.

### `backend/app/api/router.py`

Collects the event, correction, and metadata routers into one `APIRouter`.
`app/main.py` mounts this router under `/api/v1`.

For example:

```text
/api/v1 + /events + /map = /api/v1/events/map
```

### `backend/app/api/routes/__init__.py`

Marks the routes directory as a Python package. It is intentionally empty.

### `backend/app/api/routes/events.py`

Contains the main read APIs.

#### `GET /api/v1/events`

Returns a paginated event feed. It supports:

- city filtering
- date range filtering
- category filtering
- JSONB attribute filtering
- newest, soonest, and ending-soon sorting

It automatically excludes unpublished and already-ended events.

#### `GET /api/v1/events/map`

Accepts a bounding box described by west, south, east, and north coordinates.
It constructs a PostGIS rectangle with `ST_MakeEnvelope` and finds points
inside it with `ST_Intersects`.

The endpoint rejects backwards or excessively large bounding boxes and returns
at most 500 markers.

#### `GET /api/v1/events/{event_id}`

Returns one complete event. It queries the event, its evidence sources, and its
status history, then assembles them into an `EventDetail` response.

Helper functions in the same file calculate `is_new`, `is_ending_soon`, date
boundaries, and the public summary representation.

### `backend/app/api/routes/corrections.py`

Provides `POST /api/v1/corrections`.

It checks that the referenced event exists, creates a correction with status
`pending`, commits it to PostgreSQL, and returns HTTP `202 Accepted`. `202`
means the submission was accepted for later review, not that it was
automatically approved.

### `backend/app/api/routes/meta.py`

Provides `GET /api/v1/meta/categories`. It maps the internal category values
such as `performance` to user-facing Chinese labels such as `演出`.

The mobile app can use this endpoint instead of maintaining a separate category
list.

## 9. Seed data

### `backend/app/seed.py`

Inserts five fictional Changsha events and two fictional sources so the mobile
team can use real API responses before collection pipelines exist.

The records are deliberately marked with `is_demo=True` and use `example.com`
URLs. They must not be presented as real public events.

The seed function first counts existing events. If any exist, it exits without
inserting duplicates. This makes it safe to run on every container startup for
the current development workflow.

## 10. Database migrations

### `backend/alembic/env.py`

Connects Alembic to this application. It loads the database URL from settings,
imports the SQLModel metadata, and supports both online migrations against a
database and offline SQL generation.

### `backend/alembic/script.py.mako`

Template used when Alembic generates a new Python migration file. It supplies
the standard revision identifiers and `upgrade()`/`downgrade()` functions.

### `backend/alembic/versions/20260910_0001_initial.py`

The first database migration. Its `upgrade()` function:

1. enables the PostGIS extension
2. creates all five tables
3. creates the PostGIS GiST spatial index
4. creates a feed index for city, start time, and category

Its `downgrade()` function removes the tables in reverse dependency order.

Alembic stores the applied revision in a database table named
`alembic_version`. Running `alembic upgrade head` only applies migrations the
database has not already recorded.

## 11. Scripts and tests

### `backend/scripts/export_openapi.py`

Loads the FastAPI application, generates its OpenAPI JSON, and writes it to:

```text
mobile/openapi.json
```

The mobile command `npm run generate:api` then turns that JSON into
`mobile/src/api/schema.d.ts`. This is the contract-first link between backend
and frontend.

### `backend/tests/test_public_contract.py`

Contains API contract tests. It currently verifies:

- the root endpoint points to the docs and health URLs
- category values have the expected Chinese labels
- an invalid map bounding box uses the shared error envelope
- the checked-in `mobile/openapi.json` still matches the FastAPI application

The final test intentionally fails when a backend schema changes but the mobile
OpenAPI snapshot has not been regenerated.

## 12. Example request flow

For this request:

```http
GET /api/v1/events?city=长沙&category=market
```

the flow is:

1. Uvicorn receives the TCP/HTTP request on port 8000.
2. FastAPI matches the URL to `list_events()` in `events.py`.
3. FastAPI validates `city` and `category` using the function annotations.
4. `get_session()` provides a database session.
5. `list_events()` builds a SQLModel query.
6. Psycopg sends the generated SQL to PostgreSQL.
7. PostgreSQL returns matching `events` rows.
8. `_summary()` converts each database model into an `EventSummary` schema.
9. FastAPI validates and serializes the response as JSON.
10. Uvicorn sends the HTTP response to the mobile application.
11. The database session closes after the request.

## 13. Where to make common changes

| Goal | Start here | Also check |
| --- | --- | --- |
| Add an endpoint | `app/api/routes/` | Register a new router in `app/api/router.py` |
| Change response JSON | `app/schemas.py` | Export OpenAPI and regenerate mobile types |
| Add a database column | `app/models.py` | Create an Alembic migration |
| Change DB credentials | root `.env` | `compose.yml` and `app/core/config.py` |
| Change CORS origins | root `.env` | `app/core/config.py` |
| Add demo events | `app/seed.py` | Recreate the local volume if old seed data exists |
| Change map queries | `app/api/routes/events.py` | PostGIS indexes in migrations |
| Add a dependency | `pyproject.toml` | Run `uv lock`/`uv sync`, then rebuild Docker |
| Change startup behavior | `Dockerfile` | `compose.yml` |

## 14. Useful commands

Run from the repository root unless otherwise noted.

```powershell
# Start or rebuild the API and database
docker compose up --build

# Show running services
docker compose ps

# Follow API logs
docker compose logs -f api

# Open a shell inside the API container
docker compose exec api sh

# Open PostgreSQL's command-line client
docker compose exec db psql -U citypulse -d citypulse

# Apply pending migrations manually
docker compose exec api alembic upgrade head

# Run backend tests inside the API container
docker compose exec api python -m pytest
```

The production API image currently installs runtime dependencies only, so the
last command requires the development dependencies to be installed or tests to
be run through the local `uv` environment instead:

```powershell
cd backend
uv sync --all-extras
uv run ruff check app tests
uv run pytest
```

## 15. Current development limitations

- Backend source is copied into the Docker image; code changes require a rebuild.
- Seed data is fictional and not a collection pipeline.
- Corrections are stored but there is no reviewer/admin interface yet.
- Favorites are currently stored on the mobile device rather than the backend.
- Authentication, rate limiting, background workers, and monitoring are future work.
- The Compose credentials and exposed database port are for local development,
  not a production deployment configuration.
